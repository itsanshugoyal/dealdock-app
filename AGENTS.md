# AGENTS.md

Rules for anyone (human or agent) changing this repo. Architecture lives in ARCHITECTURE.md, design in DESIGN.md, open launch gates in pending.md. `apps/web/AGENTS.md` is generated by Next.js; don't edit it.

## Checks

`npm run typecheck`, `npm run lint` (architecture boundaries) and `npm test` run locally. The integration and browser gates (`npm run test:integration`, `npm run test:browser`) need Postgres, Redis and a browser; don't claim them unless they actually ran.

## Repo invariants

- **Nothing auto-sends.** A message goes out only through the API send route, after an authenticated seat approves a specific draft with an idempotency key (`apps/api/src/routes/threads.ts`, ARCHITECTURE.md §6.2). Drafts, comment-lead replies, reminders and invoice notes are drafts until a person sends them.
- **The worker can't send messages.** `scripts/boundary-rules.mjs` blocks the worker from importing `@dealdock/messaging`, Graph adapters or send/decrypt helpers, and from naming Graph hosts. `apps/worker/src/refuse-api-secrets.ts` makes it exit at startup if Meta, Google or token-encryption credentials are in its env.
- **The web never imports `@dealdock/ai` or `@dealdock/messaging`.** Provider capabilities live in the API.
- **Money is integer minor units**, never floats.

## Feature flags

One registry, `packages/core/src/feature-flags.ts` (`FEATURE_FLAGS`, exported from `@dealdock/core`). Every flag in the repo goes there; don't read `process.env` for a feature anywhere else.

- **Server:** `isFeatureEnabled("name")` (or `featureFlags()` for all of them). The value must be exactly `"true"` or `"false"`. Anything else gives the default.
- **Web:** never reads env. The API sends the flags as `features` on `GET /dashboard`. The web stores them in `AppSnapshot.features` and screens read them with `useFeature("name")` / `useFeatures()` (`apps/web/src/lib/use-demo.ts`). Until the API answers, and in demo mode, the web uses the registry defaults.

**Adding a flag:** add an entry `{ env, default, description }` to `FEATURE_FLAGS`, document the env var in `.env.example` under "Feature flags", gate the API routes and every UI entry point, and test both states.

**When a flag is required:** every big new feature ships behind one. That means a new surface, a new external provider or permission, anything that needs third-party approval (Meta, Google, payment rails), legal or tax review, or a risky change to existing behaviour.

**Practices:**

- Pick a safe default: off for anything not yet approved or reviewed.
- The server decides. The web only reads `features`.
- Use one flag per feature, not one per component.
- Gate the API routes as well as the UI. A disabled feature answers `404 { error: "feature_disabled" }` (the `META_*` flags keep their older responses). Hide its UI completely, with no dead buttons and no empty states that point at it.
- Never put security, auth, validation or tenant isolation behind a flag.
- Test both states: the API refusal and the web hiding.
- Remove the flag once the feature is fully rolled out. Track the removal in pending.md.

Current flags: `invoices` (`FEATURE_INVOICES_ENABLED`, default on, to be set to `"false"` in production until a chartered accountant signs off), and `humanAgent`, `insights`, `commentLeads` (`META_*`, default off until Meta approves).
