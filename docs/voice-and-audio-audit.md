# Voice and audio audit

31 October 2026. This is a read-only code and product-document review, not a live Meta or creator-account test. It describes the current implementation and gaps; it does not establish a new milestone.

## Written voice: what is implemented

- Onboarding can record explicit voice consent for an Instagram account. Live onboarding saves consent but does not initiate style extraction. Settings offers a manual refresh; the refresh endpoint uses the first connected account and requires consent and at least three stored outbound messages. Automatic weekly refresh is deferred. See `apps/api/src/routes/onboarding.ts:27`, `apps/web/src/components/live-onboarding.tsx:21`, `apps/api/src/routes/settings.ts:60`, and `apps/web/src/components/live-settings.tsx:24`.
- A refresh selects the 30 most recent stored outbound messages by default for that organization and account and extracts a style card. Selection currently does not filter for text content or exclude empty messages. The resulting card and message IDs are saved only after consent and its version are checked again. Revocation clears the card and sample IDs and discards ready or edited drafts for that account. See `packages/db/src/repos/voice.ts:10` and `packages/db/src/repos/voice.ts:37`.
- The API's history scan fetches available conversations and messages, maps outbound direction, and enqueues records for persistence; the ingestion worker writes message rows. Native Instagram send echoes are also mapped outbound. The leak scan asks for 30 days, while recurring scans use a checkpoint. This code does not establish access to every historical DM or unlimited history, and real Meta behavior was not tested here. See `apps/api/src/graph-maintenance.ts:18`, `apps/api/src/graph-maintenance.ts:50`, `packages/messaging/src/instagram/instagram-graph-adapter.ts:116`, `packages/messaging/src/instagram/instagram-graph-adapter.ts:168`, and `packages/db/src/repos/ingestion.ts:96`.
- Drafting requires active consent and passes the account's style card and current thread history to the prompt. With consent but no card, the prompt specifies a generic style. The implementation does not separately retrieve the 5–8 sent-message exemplars described in the architecture. There is no per-creator model fine-tuning. See `apps/api/src/routes/threads.ts:75`, `apps/worker/src/consumers/drafting.ts:39`, `packages/ai/src/prompts.ts:98`, and `ARCHITECTURE.md:244`.
- Up to ten account-scoped past overrides feed the **classification** prompt; they do not establish automatic writing-style learning. The system records original and final reply text and edit distance for sent drafts, but this is not an automatic style-training loop. See `packages/db/src/repos/creator-context.ts:25`, `packages/ai/src/prompts.ts:62`, and `packages/db/src/repos/drafts.ts:276`.
- Sampling currently selects outgoing messages from the Instagram account; it does not distinguish native creator-authored text from earlier DealDock-assisted or teammate-written replies. That is not proof of which individual typed a native Instagram message. Initial sample curation/provenance should prevent unrepresentative or mostly AI-authored replies from becoming the creator's style reference; subsequent human edits should be evaluated before influencing refreshes. The current query has no source/actor exclusion: `packages/db/src/repos/voice.ts:18`.
- A person reviews and approves the text before the API sends it. Graph credentials and provider I/O are owned by the API; the worker does not send replies. See `apps/web/src/components/live-thread.tsx:63`, `apps/api/src/routes/threads.ts:110`, and `apps/api/src/graph-maintenance.ts:18`.

The Instagram connection grants the product permission to ingest available conversation data for its core inbox/classification functions. The additional writing-style consent controls using outgoing replies for style extraction and drafting; it does not turn all historical ingestion on or off. The creator's outgoing text supplies the writing style, while the current buyer conversation supplies reply context. A shared configured Claude model receives that account's context; a separate model is not trained for every person.

## Storage and scope

The schema uses shared PostgreSQL tables, not a separate database for each creator. `Thread` carries organization and Instagram-account IDs; `Message` carries organization and thread IDs; `VoiceProfile` has one unique profile per Instagram account, including organization ID, consent, style card, and sample IDs. Scoped repository queries select the account's profile and corrections; the business context and currency supplied alongside them are organization-wide. See `packages/db/prisma/schema.prisma:9`, `packages/db/prisma/schema.prisma:203`, `packages/db/prisma/schema.prisma:231`, `packages/db/prisma/schema.prisma:266`, `packages/db/prisma/schema.prisma:381`, and `packages/db/src/repos/creator-context.ts:21`.

This is application-level scoping, not a claim of absolute isolation. PostgreSQL row-level security remains outside the documented pilot remediation; see `docs/private-pilot-readiness.md:29`.

## Audio: current gaps

The schema can label audio and the classification worker routes non-text content to review with a needs-your-ear rationale. However, the live webhook and history paths label textless messages as generic attachments, and text-bearing messages as text; they do not reliably identify voice notes as audio. The live thread displays text only and has no audio player. No transcription, voice cloning, or audio reply sending is implemented in the inspected flow; the provider send interface takes text. See `apps/api/src/routes/webhooks.ts:103`, `apps/api/src/graph-maintenance.ts:39`, `apps/worker/src/consumers/classification.ts:42`, `apps/web/src/components/live-thread.tsx:9`, `apps/web/src/components/live-thread.tsx:57`, and `packages/messaging/src/instagram/instagram-graph-adapter.ts:209`. The PRD places audio transcription and classification in V1, after the pilot: `DealDock_Product_PRD.md:198` and `DealDock_Product_PRD.md:343`.

## Proposed next step — not implemented

First scope a small written-style improvement: make initial account-specific refresh discoverable after consent and available history, filter usable text samples, expose insufficient-sample and refresh failures, and verify drafts and tenant/account boundaries with meaningful tests. Keep human approval for sending. Validate real provider permissions and history behavior separately before promising coverage. Any audio detection, playback, transcription, voice cloning, or audio sending should be a separate proposal and approval, with its own provider feasibility and privacy review.

The new [Studio HTML](../design/studio/dealdock-studio.html) illustrates a possible interface for source sample selection, editable writing preferences, separate creator profiles and a local preview. Those controls run on fictional in-memory data and are not wired to this backend. Its manual audio-review/text-reply demonstration is also proposed UX, not a claim that the existing product supports audio playback or a consent-free manual send flow.
